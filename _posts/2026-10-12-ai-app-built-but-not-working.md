最开始，AI 告诉我 App 已经做好了。

构建通过了，安装包也生成了。我把 APK 安装到手机上，等着它按照设定的时间提醒我，结果**没有收到通知**。

这不是一个复杂到需要海量用户才能发现的问题。提醒就是这个 App 的核心功能，而我作为真实用户，安装之后很快就碰到了问题。

后来又遇到另一个交付问题：新版本虽然能打包，但签名和旧版本不一致，无法直接覆盖安装。如果只能先卸载再安装，原来保存的设置就可能丢失。

这两件事让我重新审视一个习以为常的说法：**“AI 已经把 App 做好了。”**

它到底意味着代码写完、构建通过，还是用户能够正常安装、持续使用和升级？

## 一、构建成功，为什么还收不到通知？

这个 App 用来提醒我在工作期间适时活动。我真正需要的不是一个能打开的界面，而是：设置好提醒时段后，即使手机锁屏、没有继续操作屏幕，到了时间也能收到提醒。

早期的验证关注了几个比较容易执行的环节：工程能不能构建，APK 能不能生成，测试按钮能不能主动发出一条通知。

这些检查有价值，但覆盖的不是同一件事：

| 已检查的环节 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 构建成功 | 代码和构建配置能产出安装包 | App 的业务功能在手机上正确运行 |
| 安装成功 | 安装包能被目标设备接受 | 后台调度和通知按预期执行 |
| 测试按钮发出通知 | 当前执行条件下具备显示通知的能力 | 锁屏后定时任务会在指定时间触发 |
| 实际锁屏等待提醒 | 在这次设备、权限、系统状态下完成端到端验证 | 跨天、重启、其他机型也必然可靠 |

最关键的差异，是**“主动触发通知”不等于“到点自动触发通知”**。

测试按钮走的是人为即时触发路径；日常提醒则还涉及保存配置、安排调度、系统后台限制、锁屏状态和通知展示。任何一个环节出现问题，用户看到的结果都是“没有提醒”。

当时最初的误判，就是用前面几个局部成功，推导出整条业务链路已经完成。

## 二、真实使用路径，应该成为验收入口

如果重新设计这一功能的验收方式，我会先写用户路径，而不是先看 AI 生成了多少条自动化测试。

例如，最小的一条端到端路径是：

1. 安装 App，授予所需通知权限。
2. 配置提醒时段并保存。
3. 退出设置页，让手机进入锁屏状态。
4. 不再主动点击测试按钮，也不触碰屏幕。
5. 等到设定的提醒时间，观察通知是否出现，并记录实际到达时间。

这条路径的结果，比“通知 API 调用成功”更接近用户真正关心的事情。

当然，一次成功也不意味着所有环境都可靠。还要逐步覆盖重新打开 App 后设置是否保留、跨天是否继续调度、设备重启后会怎样，以及不同 Android 设备和系统省电策略下的表现。

因此，测试结果需要带上环境和边界，而不是只写一个笼统的“通过”。

对 Agent 而言也是一样。一个验证结论至少要能回答：

- **执行了什么**：是单元测试、构建检查，还是装机后的真实操作？
- **观察到了什么**：是日志显示调度成功，还是锁屏时真的出现了通知？
- **还没有验证什么**：哪些设备、系统状态和时间跨度尚未覆盖？

没有观察证据的“应该可以”，不能被记录为“已经通过”。

## 三、签名问题：为什么新版本不能覆盖安装？

通知问题之后，App 继续迭代，也增加了更多动作和交付能力。新的问题出现在升级环节。

前后两个 APK 使用了不一致的签名，导致新安装包不能直接覆盖旧版本。用户要继续使用新版本，就可能不得不卸载旧版再安装。

但对一个需要长期保存提醒时段的 App 而言，升级不能只关心“新版能安装”，还要关心**旧版的用户状态能否留下来**。

Android 对同一应用的正常覆盖升级有签名身份约束。即便包名相同，签名不匹配也不能按普通升级路径完成替换。这里讨论的是普通应用升级，不涉及 Android 官方支持的特定签名轮换机制。

这次迭代随后固定了签名机制，并把覆盖升级、保留设置纳入验证。

需要区分的是：固定签名解决的是后续版本的签名连续性；它不能让一个已经使用不兼容签名安装的旧包自动具备无损升级能力。后续发布还必须妥善保管签名密钥，不能把密钥或密码提交到公开仓库。

对于长期使用的软件，**安装、升级、数据保留，本来就是同一条交付链路**。

## 四、我后来改变了“完成”的判据

这次 App 已推进到 v0.2.0：Android APK、Windows 安装包和便携包已经发布，构建和自动化验证也已完成。

但这并不代表所有真实场景都完成验收。当前仍需继续验证 Android 跨天与不同设备的锁屏提醒，以及 Windows 锁屏时的提醒行为。此前还出现过需要每天重新保存提醒时段的现象，这类长期状态问题也不能只靠一次安装测试排除。

我现在更愿意把交付拆成几个可核实的状态：

| 交付状态 | 判据 |
| --- | --- |
| 可构建 | 在明确的构建环境中成功产出安装包 |
| 可安装 | 目标设备上能够安装和启动 |
| 核心功能可用 | 在真实使用路径中观察到预期结果 |
| 可升级 | 使用一致的签名和升级路径，覆盖安装后关键设置仍然保留 |
| 持续可靠 | 跨天、重启、锁屏和目标设备差异等场景有足够的回归证据 |

这些状态不是必须等全部完成才能发布，而是**不能把某一层的通过，冒充更高一层的通过**。

如果只完成了构建和安装，那就说“安装包已产出并通过安装检查”；如果锁屏提醒尚未经过真实验证，就明确写“待验收”。这样的表述可能没有“全部完成”那么好看，但更有用。

## 五、这也是 Agent Reliability 问题

表面上看，这只是一个小 App 的两次问题：一次没提醒，一次不能覆盖升级。

放到 AI 工程流程里，问题却很典型：

**Agent 负责生成和执行，验证系统负责提供独立证据，交付结论必须受证据约束。**

Agent 可以运行构建命令，可以编写测试，也可以根据日志解释问题。但如果它运行的是一条方便测试的替代路径，就不能把结果等同于用户的真实路径；如果它只验证了新安装，也不能推导出老用户升级后设置不会丢失。

更有效的改进不是无限增加测试数量，而是先识别**最能推翻“功能完成”结论的关键路径**。

对这个提醒 App，第一条是“设置提醒 → 锁屏等待 → 实际收到通知”；第二条是“安装旧版并保存设置 → 覆盖安装新版 → 设置仍然存在”。先把这两条跑通并保留证据，再考虑扩展其他测试，验证成本才真正用在风险上。

我不会因为这次发布成功，就宣布 App 已经彻底可靠。跨天、不同设备和锁屏状态的结果还需要真实验证。

这次经历给我的结论很简单：

**AI 能把代码写出来，但交付完成与否，必须由真实使用路径和可复核的证据决定。**

对软件可靠性而言，重要的不是 Agent 说了多少次“已经完成”，而是我们能明确指出：它完成了什么、证据在哪里、还有哪些事情尚未证明。
