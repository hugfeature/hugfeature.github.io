> **AI Eval 系列 #14**  
> 前文已经讨论了[需求不完整时 Gate 应该怎么判](/eval/test-case-gates-with-incomplete-requirements/)、[一条需求缺口应该挡住哪些用例](/eval/test-case-gate-dependency-scope/)，以及[计算类测试如何建立判据](/eval/calculation-test-oracles-and-data/)。这一篇继续回答：在人参与的前提下，评审应该放在生成链路的哪个位置。

测试用例生成 Agent 最容易展示的结果，是一次生成几十条甚至上百条用例。

数量很多，看起来覆盖充分；但真正开始评审时，问题往往出现在更前面：场景拆分是否合理，业务主线有没有遗漏，风险重点是否找对，预期结果有没有可信依据。

如果这些问题直到详细用例生成完才被发现，后面大量步骤、测试数据和预期结果都要一起返工。Agent 写得越快，返工规模反而可能越大。

我最近把一条测试用例生成流程调整为：**先输出测试场景和测试点，人工确认方案，再让程序展开详细用例。** 这不是把所有内容都交给人工审批，而是把人的判断放在仍然能够低成本改变方向的位置。

## 一、直接生成用例，把两类工作混在了一起

从需求直接生成详细用例，通常同时做了两类性质不同的工作。

第一类是需要判断的工作：

- 哪些业务流程属于本次范围；
- 哪些规则风险最高；
- 正常、异常、边界和状态流转应该怎样拆；
- 哪些内容有依据，哪些仍然未知；
- 用什么观察结果判断实现正确。

第二类是可以稳定展开的工作：

- 按已确认测试点补齐前置条件；
- 把字段和值写入操作步骤；
- 组织测试数据；
- 按固定格式生成 CSV、脑图或用例平台字段；
- 维护方案与用例之间的追溯关系。

前一类如果判断错了，后一类做得再完整也没有意义。把两类工作放在一次生成中，会让评审者面对大量细节，却很难判断最上层的方向是否正确。

## 二、测试方案不是缩短版用例

这里所说的测试方案，不需要写到每一步点击和每个字段值。它更像一份可评审的测试设计中间产物。

一个测试点至少应该回答：

| 要素 | 需要回答的问题 |
| --- | --- |
| 场景 | 在什么业务流程或状态下验证？ |
| 风险 | 这条测试主要防止什么错误？ |
| 依据 | 对应哪条需求、原型或已确认规则？ |
| 方法 | 使用等价类、边界、状态转换，还是错误推测？ |
| 判据 | 观察到什么才能判断正确或错误？ |
| 未知项 | 当前还缺什么信息，影响哪些范围？ |

例如，一个计算功能的方案可以先写：

```yaml
scenario: 优惠后计算服务费
risk: 服务费错误地按优惠前金额计算
source: 已确认的计费规则 R-07
method: 错误推测 + 区分性数据
test_point: 选择优惠金额和费率均非零的数据
oracle: 独立按 R-07 计算应付金额
unknowns: []
```

评审通过后，Agent 才继续生成实际字段、数据、操作步骤和预期结果。

这份方案的价值不是格式，而是让评审者能够在少量信息中判断：为什么要测、准备怎么测、依据是否成立。

## 三、人工评审应该决定什么

人工评审不应该逐句润色 Agent 的表达，也不应该替 Agent 补齐所有机械细节。最值得保留给人的，是下面四类决定。

### 1. 范围是否正确

方案有没有覆盖本次真正要交付的业务主线？是否把无关功能扩大进来？某条规则缺失时，影响的是一个测试点，还是整组场景？

### 2. 风险是否值得测

不是所有字段都需要相同强度。权限、金额计算、状态流转、重复提交和跨模块数据一致性，通常比普通文案和默认展示更需要明确的错误假设与判据。

### 3. 判据是否站得住

“页面正常”“结果正确”不是可执行判据。评审要确认预期来自已知规则、独立计算或可核对状态，而不是照抄被测系统输出。

### 4. 未知项如何处理

需求没有确认的规则，要保留成待确认项；当前读取范围没找到的信息，要继续核对证据。人工可以决定是否补充规则、缩小范围或暂缓相关测试，但不能让 Agent 用常识把未知项改写成事实。

评审完成后，应输出明确结论，而不是一段模糊意见：

```json
{
  "plan_version": "plan-2026-10-16-v1",
  "decision": "approved_with_gaps",
  "approved_test_points": ["TP-01", "TP-02", "TP-04"],
  "blocked_test_points": ["TP-03"],
  "open_questions": ["G-01"],
  "review_scope": "scenario-risk-oracle"
}
```

这些字段只是设计示例，不是行业通用标准。重要的是让后续生成知道哪些内容可以继续，哪些内容仍然不能形成确定预期。

## 四、评审通过后，后面应该尽量变成确定执行

方案确认后，详细用例生成不应再次自由解释需求。

更合理的契约是：

1. 每条详细用例必须关联一个已批准测试点；
2. 不得新增方案之外的业务规则和确定预期；
3. 允许选择有依据的代表值和边界值，但不得虚构产品事实；
4. 字段、输入值、操作和预期必须一一对应；
5. 发现方案无法展开时，返回缺口，不自行改变方案；
6. 输出完成后检查方案与用例之间是否发生漂移。

这时 Validator 可以更机械，也更容易稳定：检查追溯关系、必填字段、格式、重复项、被阻塞测试点是否误生成，以及方案之外是否出现新增断言。

它不需要重新发明一套测试策略。测试设计已经在上一阶段完成，后续重点是忠实展开。

## 五、这不是再加一道统一 Gate

“先评审方案”很容易被实现成另一个阻塞所有工作的总开关。如果方案里只有一个局部未知项，却让所有测试点都无法继续，就会重现此前讨论过的 Gate 粒度问题。

更合适的做法是按测试点或共享前提记录状态：

| 状态 | 后续动作 |
| --- | --- |
| approved | 可以生成详细用例 |
| revise | 修改方案后重新评审 |
| blocked_by_gap | 等待规则或证据，不生成确定预期 |
| excluded | 不属于当前范围 |

如果多个测试点共同依赖同一权限模型或状态机，缺口应该阻塞这个依赖范围；如果缺口只影响一条异常场景，就不必阻止其他独立测试点继续。

## 六、公开项目正在把“先确认计划”做成 Runtime 能力

这种分阶段设计不只适用于测试用例生成。

AgentScope 在实验性的 SOP 模块中，把任务拆成有顺序的里程碑，每一步验证后再进入下一步，并支持持久化、恢复和人工评审步骤。其 2.0.10 版本又修复了步骤主动标记失败时未被正确处理的问题。[AgentScope v2.0.9](https://github.com/agentscope-ai/agentscope/releases/tag/v2.0.9) · [v2.0.10](https://github.com/agentscope-ai/agentscope/releases/tag/v2.0.10)

Qwen Code v0.25.2 增加了 durable team plan approval、测试失败浏览器、只读探索的收敛提醒，以及子工作树任务在合并或停止后的状态收口。这些变化说明，多 Agent 系统开始把计划批准、执行状态和失败证据当成 Runtime 对象，而不只是聊天文本。[Qwen Code v0.25.2](https://github.com/QwenLM/qwen-code/releases/tag/v0.25.2)

DeepSeek Harness v0.2.1-alpha.3 则支持为子智能体配置独立预设，并改进委派深度、等待轮次、会话恢复和异常退出后的任务状态显示。[DeepSeek Harness v0.2.1-alpha.3](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.1-alpha.3)

这些项目的具体实现不同，不能直接证明“方案先审”一定适合所有业务；但它们共同提供了一个工程信号：**计划、批准、执行和完成状态正在从 Prompt 约定变成可持久化、可检查的运行时状态。**

## 七、怎么验证这次流程调整是否真的有效

不能只因为增加了评审阶段，就宣称质量提升。可以固定一批需求样本，对比“直接生成用例”和“方案评审后生成”两种路径，至少观察：

1. 业务主线、异常和边界遗漏是否减少；
2. 无依据的业务断言是否减少；
3. 能区分候选错误实现的测试点是否增加；
4. 方案批准后，详细用例是否出现新增规则或范围漂移；
5. 人工总评审时间是下降还是转移到了前面；
6. 被打回时，需要重写的是少量测试点，还是整批详细用例。

这组指标需要来自实际对照，不能预先写成成果。尤其要防止一个假象：用例数量减少了、评审变快了，但关键风险也被一起删掉。

## 结语

测试用例生成 Agent 的价值，不是一次写出最多的用例，而是把人的判断和机器的执行放在合适的位置。

人在方案阶段确认范围、风险、判据和未知项；Agent 在批准之后稳定展开步骤、数据和格式；Validator 检查生成结果有没有偏离方案。

这条链路真正想实现的不是“人审所有内容”，而是：**让人在方向仍然容易修改时作出决定，把已经确定的部分交给程序执行。**

当详细用例出现问题时，也能够反向判断是方案错了、展开漂移了，还是输入仍有缺口，而不是把所有失败都归结为“模型生成得不好”。
