给 Agent 增加 Gate，通常是为了让它更可靠。

但在一次“超长需求文档生成测试用例”的实践中，我遇到了相反的结果：需求解析、覆盖规划和用例生成前后都设置了校验，只要关键字段缺失、规则冲突或证据不足就拒绝继续。单看每条规则都合理，组合起来却让 Agent 反复卡在中间，几个小时后仍没有生成可评审的用例。

问题不是 Gate 太严格，而是**所有 Gate 都只有通过和拒绝两种结果**。

## 没有产出，不等于更可靠

传统 CI 的输入通常比较确定：代码、依赖和测试环境都有明确格式。单元测试失败，阻止合并是合理的。

Agent 面对的输入经常不完整。需求文档可能几十万字，业务规则散落在表格、原型和历史说明中；同一字段可能存在多种口径，一些测试预期只能标记为待确认。如果把所有不确定性都当成前置错误，Agent 最终会出现三种行为：

1. 反复读取和分析，消耗大量 Token，却无法跨过 Gate；
2. 为了通过校验，把未知信息补成看似确定的结论；
3. 直接终止，既没有可用产物，也没有足够证据帮助人工判断。

第三种看起来最保守，实际却可能让系统失去改进机会。没有产物就无法评审，没有 Trace 就无法归因，也无法把这次失败沉淀成 Regression Case。

所以门禁的目标不应该是“尽早拒绝所有问题”，而应该是：**让不可接受的风险停下来，让可恢复的不确定性带着证据继续。**

## 先区分风险，而不是先决定拒绝

我现在更倾向把问题分为三类。

第一类是**不可逆风险**。例如删除数据、越权写入、向外部发送敏感内容、修改范围明显超出任务边界。这类问题必须在动作发生前硬阻断。

第二类是**质量不确定性**。例如需求没有说明异常流程、某个字段的取值范围缺失、两个来源存在冲突。这类问题不应被静默补全，但通常可以标记为 Gap，继续生成带有待确认项的产物。

第三类是**可恢复的执行问题**。例如读取某个章节失败、解析表格不完整、一次工具调用超时。它们适合有限重试、切换解析方式或降级输出，而不是直接宣告整个任务失败。

分类之后，Gate 的结果就不再只有 PASS 和 FAIL，而可以是：

```text
PASS            允许继续
DEGRADED        降级继续，必须记录缺口和影响
RETRYABLE       在预算内重试或切换执行路径
NEEDS_REVIEW    产出结果，但进入人工评审
BLOCKED         立即停止，禁止产生副作用
```

这五种状态比继续增加规则更重要，因为它们决定规则如何影响执行。

## 同一 Runtime，两种执行策略

另一个容易走偏的做法，是为“快速出结果”和“高可靠交付”分别建设两套 Agent。这样做初期直观，长期却会产生两套解析器、两套工具和两套 Trace，问题无法复用。

更稳妥的方式是共用同一 Runtime，只切换执行策略。

### 探索策略：先得到可评审证据

探索策略的目标不是直接交付，而是在有限时间和成本内形成完整轮廓：

- 固定读取最相关的章节，其余内容按需检索；
- 对缺失规则显式生成 Gap，不虚构答案；
- 局部失败不终止全部任务；
- 保存解析结果、覆盖计划、失败步骤和证据引用；
- 产物标记为 `NEEDS_REVIEW`，不能自动进入正式系统。

它牺牲的是一次到位的确定性，换来的是可见结果、真实失败和人工反馈入口。

### 交付策略：把已知路径升级为稳定执行

交付策略复用同一套执行器，但要求更强的约束：

- 输入、规则和资源范围必须满足最低契约；
- 关键业务规则必须有来源；
- 生成结果经过确定性格式检查和独立质量评估；
- 未解决冲突不能伪装成确定结论；
- 失败可以复现，关键路径可以回放；
- 只有证据齐全的结果才能进入发布或上传 Gate。

两种策略不是固定的先后流水线。新场景可以先探索再升级；已经稳定、有完整契约的场景也可以直接走交付策略。真正需要统一的是状态、Trace、错误分类和证据格式。

## Gate 应该放在什么位置

一个长任务至少需要四类 Gate，它们解决的问题不同。

### 1. Admission Gate：任务是否值得开始

检查输入能否读取、任务目标是否明确、运行预算是否足够。这里不要求需求完整，只需要判断能否开始收集证据。

### 2. Progress Gate：是否还能有效继续

监控重复读取、连续失败、无进展步骤和上下文膨胀。如果继续执行只会烧 Token，应降级、暂停或请求人工，而不是无限重试。

### 3. Quality Gate：产物处于什么质量状态

检查覆盖缺口、来源冲突、格式错误和未验证假设。它可以输出 `DEGRADED` 或 `NEEDS_REVIEW`，不必把所有问题升级为任务失败。

### 4. Delivery Gate：是否允许进入下游系统

只有这里需要执行最严格的准入。未经人工评审或证据不足的测试用例，可以生成、查看和修改，但不能直接上传正式用例库或触发后续自动执行。

关键区别是：**Quality Gate 决定结果是什么状态，Delivery Gate 决定结果能去哪里。** 把两者合并，往往就是“质量不确定，所以什么都不生成”的根源。

## 如何判断门禁是否过度

Gate 本身也需要被评测。至少记录下面五个指标：

- 任务完成率；
- 各 Gate 的拒绝率和主要原因；
- 从开始到首个可评审产物的时间；
- 人工接受、修改和退回比例；
- 每个有效产物消耗的 Token、步骤和重试次数。

如果 Gate 拒绝率持续升高，但进入人工评审后的错误并没有减少，它很可能只是把失败提前了；如果放宽某类规则后产物增加，同时缺口被明确标记且没有进入正式交付，就说明降级策略比硬拒绝更有效。

## 行业信号也在转向分层监督

GitHub 已经把 Coding Agent 推向定时任务、跨会话继续和自动处理合并前问题。Agent 越来越可能在无人盯守时运行，单一的“遇事暂停等待确认”会成为新的卡点。

Anthropic 公布的内部监督方案则提供了另一个参照：不可逆危险由在线监控在动作前阻断，慢性、可恢复的问题进入离线监控和人工升级。其公开数据中，在线监控覆盖全部动作，但实际阻断比例只有约 0.002%。这说明覆盖全面并不等于处处硬拒绝。

另一方面，Arena 对 21 种模型与 Harness 组合的测试显示，相近成功率下，同一模型的成本最高可相差数倍。过度规划、重复验证和无效重试不只是体验问题，也会直接变成 Harness 成本。

## 结语

Agent Reliability 不是给执行链路不断增加关卡，而是让每一个风险进入正确的处理通道。

不可逆风险要阻断，信息缺口要暴露，可恢复失败要有预算地重试，质量不确定的产物要进入人工评审，只有满足证据契约的结果才能进入正式交付。

真正可靠的 Gate，不是让 Agent 更难通过，而是让系统始终知道：**现在能不能继续、结果可信到什么程度，以及它被允许走到哪里。**
